## 6. SLO болон threshold

Анхны baseline p95 нь 212.31 ms байсан.

SLO тодорхойлохдоо baseline-ийг 1.5 дахин өсгөж 318.465 ms гэж тооцсон. Үүнийг 319 ms болгон тоймлож, `p(95)<319` гэсэн босго сонгосон. Ингэснээр анхны хэмжилтээс 50% орчим удаан хариуг зөвшөөрөх зорилт тогтоосон.

Мөн HTTP хүсэлтийн алдааны хувийг 1%-иас бага байлгах `rate<0.01` шаардлага тавьсан.

| Хэмжүүр | PASS | FAIL |
|---|---:|---:|
| VU | 30 | 30 |
| p95 (ms) | 214.72 | 215.13 |
| Threshold (ms) | 319 | 50 |
| Error rate | 0% | 0% |
| Exit code | 0 | 99 |
| Үр дүн | PASS | FAIL |

PASS туршилтад хоёр threshold хоёулаа хангагдсан.

FAIL туршилтад p95-ийн босгыг зориуд 50 ms болгож хатууруулсан. Хэмжсэн p95 нь 215.13 ms байсан тул k6 threshold зөрчигдсөн тухай алдаа гаргаж, exit code 99 буцаасан.

Үр дүн:

- `results/threshold-pass.txt`
- `results/threshold-fail.txt`

## 8. Дүгнэлт

Энэ лабораторид k6 ашиглан веб серверийн гүйцэтгэлийг бодитоор хэмжсэн. Эхлээд 5 виртуал хэрэглэгчтэй тест ажиллуулж, p95 latency-ийн baseline утгыг тодорхойлсон. Дараа нь 5, 30, 100 VU-ийн гурван түвшнийг тус тусад нь туршиж харьцуулсан. Хэрэглэгчийн тоо өсөхөд throughput нэмэгдсэн боловч p95 latency бараг өөрчлөгдөөгүй. Туршилтын явцад HTTP error rate бүх түвшинд 0% байсан. Stages туршилтаар хэрэглэгчийн ачааллыг өсгөж, бууруулах үед серверийн ерөнхий гүйцэтгэлийг ажигласан. Анхны baseline-д үндэслэн p95 нь 319 ms-ээс бага байх SLO тодорхойлсон. Энэ босгыг ашигласан туршилт PASS болсон бол 50 ms-ийн хатуу босготой туршилт FAIL болсон. Ингэснээр threshold нь гүйцэтгэлийн шаардлагыг автоматаар шалгах боломжтойг ойлгосон. Лекцээр үзсэн latency, throughput, error rate болон SLO гэсэн ойлголтуудыг бодит хэмжилтээр харьцуулж сурсан.
